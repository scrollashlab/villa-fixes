# villa #1586 — `cache_max_gb` double accounting

Upstream: https://github.com/ScrollPrize/villa/issues/1586  
Evidence: `villa-1586/`  
Credit: @flummoxjr (diagnosis; prior closed PR #1587).  
Author on patch: Scroll Ash Lab \<scrollash.lab@gmail.com\> (AI-assisted)

## Problem

`open_volume_root` handed the same byte budget to (1) an open-time directory sweep and (2) a fresh zarr `CacheStore` whose in-memory LRU started empty and never scanned files left by an earlier run. Reopening an at-budget cache directory therefore spent a **second** full budget on disk (~1.9–2× steady state).

## What changed

- Snapshot the volume cache subdirectory when a budget is set.
- After constructing `CacheStore`, seed its private LRU (`_state`) from retained files (oldest-first) before `zarr.open`.
- If the installed zarr build exposes no seedable state, emit `RuntimeWarning` (fail loudly) rather than silently overshooting.
- Docs updated in ink_detection README / `docs/ink_detection.md`.

## Real-data numbers

Volume (anonymous):  
`s3://vesuvius-challenge-open-data/PHercParis4/volumes/20260411134726-2.400um-0.2m-78keV-masked.zarr`, level `3` (128³ uint8 chunks, 2 MiB each), `cache_max_gb=0.03`.  
Each run: fresh process, 20 different non-empty chunks near volume centre, then measure cache directory. Source: `real-data-2026-10-05/probe-1586-run1.txt` / README table. Villa tip for this probe: `0e14cf48`.

| Run (fresh process) | Unmodified main: cache on disk | With patch: cache on disk |
|---|---|---|
| 1 (empty cache) | 29,360,128 B (0.98× budget) | 29,360,128 B (0.98× budget) |
| 2 (reopen, new chunks) | 58,720,256 B (**1.96×** budget) | 29,360,128 B (0.98× budget) |
| 3 (reopen, new chunks) | 54,525,952 B (**1.82×** budget) | 29,360,128 B (0.98× budget) |

All 60 blocks read through the patched cache were byte-identical (SHA-256) to uncached reads of the same volume (README claim).

## Limitations

- Seeds `CacheStore._state` (no public zarr API); guarded + warned if layout changes.
- Concurrent multi-process writers can still overshoot until the next open-time sweep (documented).
- Does not fix the separate upstream zarr bug where `max_size` smaller than one chunk never tracks full-key writes.
